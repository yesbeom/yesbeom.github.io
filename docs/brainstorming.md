## 4단계: 유효 질량 근사(EMA) 심화 논의

### 당신이 제시한 정보

**유효 질량 근사 (Effective Mass Approximation, EMA)**
- 반도체 물리학 및 전산모사에서 주로 사용되는 모델
- **개념**: 크기가 매우 커서 제1원리 계산(First-principles)이 어려운 양자점의 전자 구조와 광학적 특성을 효율적으로 계산하기 위해 고안된 근사법
- **특징**: 원자 하나하나를 계산하지 않고, 물질의 주기적인 포텐셜을 '유효 질량(Effective Mass)'이라는 하나의 상수로 대체하여 슈뢰딩거 방정식을 품
- **활용**: 양자점의 크기에 따른 밴드갭 변화나 발광 스펙트럼, 나노구조의 광학 특성을 예측하는 데 널리 쓰임

### 홈페이지 내 구현 가능성

**답변: 충분히 구현 가능**

오히려 이게 딱 브라우저에서 돌리기 좋은 케이스
- 미분방정식을 실시간으로 푸는 게 아니라
- **이미 해석적으로 풀린 공식(Brus equation)**을 쓰는 거라서 계산량이 거의 없음

### Brus 방정식 상세 설명

**수식 (3항 구성)**:
$$E_g(R) = E_g(\text{bulk}) + \frac{\hbar^2 \pi^2}{2R^2}\left(\frac{1}{m_e^*} + \frac{1}{m_h^*}\right) - \frac{1.8e^2}{4\pi\varepsilon_0\varepsilon_r R}$$

- **1항**: 벌크 밴드갭 (물질 고유값)
- **2항**: **양자구속 에너지** — 입자가 작아질수록(R↓) 커짐 (유효질량으로 슈뢰딩거 방정식을 푼 부분)
- **3항**: 전자-정공 쿨롱 인력 보정 (구속 에너지를 살짝 줄여줌)

**중요**: 세 항 모두 사칙연산과 거듭제곱만으로 계산됨 → JavaScript 함수 하나로 짜면 끝

### 웹 구현 흐름

1. **파라미터 입력**: 물질 선택(InP 양자점 등 프리셋) → $E_g(bulk)$, $m_e^*$, $m_h^*$, $\varepsilon_r$ 자동 로드 / 입자 반지름 R을 슬라이더로 조절
2. **계산**: 위 공식으로 $E_g(R)$ 실시간 계산
3. **시각화**: 
   - 밴드갭 → 파장 변환 ($\lambda = hc/E_g$) → 대략적인 발광색 스와치로 표시
   - R을 x축, $E_g$를 y축으로 하는 곡선 그래프 (recharts)


### 주의사항
- 유효질량 값($m_e^*$, $m_h^*$)과 유전율($\varepsilon_r$)은 물질마다 문헌값이 다름
- 네가 실제 논문에서 쓰는 값이나 신뢰할 수 있는 출처값을 확인해서 넣는 게 좋음
- Sonnet한테 "InP 유효질량 문헌값 조사해줘" 시켜도 되고, 네가 직접 알고 있는 값을 넣어도 됨

- 기술: 경험적 근사 알고리즘
- 토큰 비용: 만들 때만, 이후 무료

### "만들 때만 비용, 이후 무료"인 이상적인 케이스 개념

**핵심 구분: 해석적 공식(analytical formula) vs 수치 시뮬레이션(numerical simulation)**

- **해석적 공식** = 사칙연산/거듭제곱으로 즉시 계산됨
  - 브라우저 JS로 순식간에 처리
  - AI 모델 호출 자체가 필요 없음 (계산은 그냥 자바스크립트 함수)
  - "토큰 사용"은 만들 때 한 번(Fable5/Sonnet이 코드 작성)만 쓰임
  - 사용자가 쓸 때는 토큰이 전혀 안 듦
  - 이미 웹페이지에 박힌 계산식이 로컬에서 도는 거라서

- **수치 시뮬레이션** = 반복계산 또는 외부 API 호출 필요
  - 토큰이 계속 사용됨

## 6단계: Electron Cloud 표현 가능성 논의

### 당신의 질문

1. **Electron cloud를 간략하게 그려볼 수 있을까?**
   - **답**: 가능하다 (방식을 바꿔야 함)

2. **SMILES 코드로 입력하는 건가?**
   - **답**: 맞다

### 상세 분석

#### Electron Cloud 간략 시각화 — 가능!
**정확한 electron density는 무리지만, 정성적 표현은 가능**

**방법: Gasteiger Partial Charge**
- 이건 실제로 존재하는 경험적 알고리즘
- 전기음성도 차이를 반복 계산해서 각 원자에 부분전하(partial charge)를 할당
- **중요**: 양자역학 계산이 아니라 **전기음성도 기반 반복 연산**
- 계산량: 매우 가벼움 (수십~수백 번의 사칙연산 반복)
- **결과**: 분자 구조 위에 원자별로 색깔을 입혀서 "대략 이쪽에 전자가 쏠려있다"는 직관적 그림을 보여줄 수 있음

**구현 흐름**:
1. **입력**: SMILES 코드 입력 (예: `CC(=O)O` = 아세트산)
2. **파싱**: SMILES를 분자 구조(원자+결합)로 변환
   - 직접 짜기보다 기존 오픈소스 라이브러리(RDKit.js) 사용
   - RDKit.js: WASM으로 컴파일된 버전 사용 가능
3. **계산**: Gasteiger charge 알고리즘 적용
   - RDKit.js에 이미 내장되어 있음
4. **시각화**: 2D 구조식 위에 색상 오버레이
   - 빨강(음전하/전자 많음) ~ 파랑(양전하/전자 적음) 그라데이션

**특징**:
- "직접 양자화학 계산"이 아니라 "잘 알려진 경험적 근사 알고리즘 + 기존 라이브러리 활용"
- 네가 우려하는 "큰 모델 필요" 영역을 벗어남
- RDKit.js 자체가 무거운 라이브러리(WASM 바이너리 몇 MB)이지만, 실행은 사용자 브라우저에서 순식간에 끝남
- 서버 비용도 안 들어감

**반드시 명시해야 할 것**:
- 이건 진짜 electron density(전자 확률 분포 함수)가 아님
- "부분전하 추정치"라는 걸 라벨링해야 과학적으로 정직한 도구가 됨
- 오해를 부르면 오히려 역효과

## 8단계: 표면/부피 비율 계산기 상세화

### 당신의 요구사항

"형태에 따른 것도 포함이 되었으면 좋겠어"
- Spherical (구형)
- Tetrahedral (사면체)
- Tetrapod (4개 다리)

"나노입자 크기를 설정할 때는 무엇을 기준으로 해야하는지도 중요"
- Spherical: 지름(또는 반지름)
- Tetrahedral: edge 길이와 수직 길이가 다르니까
- Tetrapod: 복합 파라미터 필요

### 형태별 파라미터 정의

#### Spherical (구형)
- 반지름 $R$ 하나만으로 충분
- $S/V = 3/R$ (표면적/부피 비율)

#### Tetrahedral (정사면체)
- edge length $a$ 하나로 표현 가능
- 정사면체는 정다면체라 edge 하나만 알면 부피/표면적 다 유도됨
- "edge와 수직 길이가 다르다"는 생각: 
  - 정사면체(regular tetrahedron)라면 실제로 높이(수직 길이)는 $h = a\sqrt{2/3}$으로 자동 계산됨
  - 만약 비정형 사면체라면 별도 처리 필요

#### Tetrapod (4개 다리)
- 진짜 까다로운 경우
- 4개의 다리(arm)가 뻗어 나온 구조
- "하나의 파라미터"로 정의 불가능
- **최소 필요 파라미터**:
  - arm 길이
  - arm 두께(반지름)
  - 중심 코어 크기
  - 총 3개 이상
- **근사 방식**: 각 arm을 원기둥+끝단 팁으로 근사해서 표면적/부피를 합산

### UI 설계

- 형태 선택: 드롭다운
- 형태에 맞는 파라미터 입력창이 동적으로 바뀌는 구조
  - Spherical: 반지름 하나 슬라이더
  - Tetrahedral: edge length 슬라이더
  - Tetrapod: 3개 슬라이더 (arm 길이, arm 두께, 코어 크기)
- 이것도 전부 기하 공식이라 계산은 가벼움
- 만들 때만 신경 쓰면 이후엔 무료로 작동

## 9단계: 모델별 역할 분배

"클로드 내의 모델들 Fable, opus, sonnet, haiku 에게 일을 어떻게 배분해야할까?"

### 전체 원칙

**작업 성격에 따라 나누기**:
- **설계/검증/판단 + 실제 코드 작성** (리서치부터 구현까지) → Sonnet
- **아주 단순 반복 작업** (포맷팅, 텍스트 변환) → Haiku
- **전체 지휘/조율** → Fable5

### 프로젝트별 역할 분배

#### 1) 양자구속 계산기 (EMA/Brus)

| 작업 | 담당 | 이유 |
|---|---|---|
| 물질별 유효질량/유전율 문헌값 조사 | **Sonnet** | 이미 어떤 값을 찾아야 하는지(유효질량, 유전율) 명확해서 리서치+정리까지 Sonnet이 처리 가능 |
| Brus equation → JS 함수 구현 | **Sonnet** | 이미 공식이 정해져 있으니 그대로 코딩만 하면 됨 |
| 밴드갭→색상 변환(파장→RGB) 로직 | **Sonnet** | 표준 변환 공식, 패턴화된 작업 |
| 슬라이더/그래프 UI | **Sonnet** | React+recharts 보일러플레이트 |
| 최종 물리적 타당성 검증 | **Sonnet** (또는 너 본인) | 여기가 제일 중요 — 네 전문성으로 직접 크로스체크 추천 |

#### 2) 표면/부피 비율 계산기

| 작업 | 담당 | 이유 |
|---|---|---|
| 형태별(구/사면체/테트라포드) 기하 공식 유도 | **Sonnet** | 테트라포드 근사 방식(원기둥+팁)이 이미 이 문서에 정의돼 있어 그대로 적용해 유도 가능 |
| 공식 → JS 함수 변환 | **Sonnet** | 공식이 나오면 코딩은 단순 |
| 동적 입력 UI (형태 선택시 파라미터 바뀜) | **Sonnet** | 프론트엔드 로직, 패턴화됨 |

#### 3) Electron Cloud (Gasteiger charge)

| 작업 | 담당 | 이유 |
|---|---|---|
| RDKit.js 통합 방법 조사 (WASM 로딩, API) | **Sonnet** | 공개 문서가 있는 라이브러리 조사라 Sonnet이 직접 리서치 후 구현까지 이어갈 수 있음 |
| SMILES 입력 → 파싱 → 시각화 파이프라인 구현 | **Sonnet** | 일단 조사가 끝나면 구현은 표준 패턴 |
| 색상 스케일(빨강~파랑) 매핑 | **Haiku** | 단순 그라데이션 함수, 아주 쉬움 |
| "이건 정확한 electron density가 아니다" 안내 문구 작성 | **Haiku** | 단순 텍스트 작성 |

#### 전체 조율 (Fable5)

- 세 계산기를 하나의 페이지/탭 구조로 묶는 전체 아키텍처 설계
- 각 서브태스크를 위 표처럼 나눠서 Opus/Sonnet/Haiku에게 지시
- 세 계산기 사이 디자인 일관성(공통 컴포넌트, 스타일) 관리
- 최종 통합 후 전체 동작 점검

### 실전 팁

- **순서 중요**: Sonnet에게 먼저 "무엇을 계산할지(공식/알고리즘)"를 리서치/확정하게 한 뒤, 그 다음 단계로 "이 공식을 코드로 짜줘"라고 이어서 진행하는 게 효율적
- **역순의 위험**: 공식이 확정되지 않은 채 코딩부터 시키면 잘못된 근사로 코딩해버릴 위험 있음
- **너의 검수**: 물리/화학적으로 맞는지 최종 검수는 AI에게만 맡기지 말고 직접 확인하기
  - 특히 EMA 문헌값, tetrapod 근사 방식
  - 이게 "AI를 잘 활용하는 능력"을 보여주는 핵심 포인트

## 10단계: 프로그래밍 개념 적용 (구현 전 확인)

### 당신의 질문

"프로그래머들과 이야기를 나누니까 플로우 차트, 아키텍처, 폴더 트리, 루프 엔지니어링 과 같은 내용을 강조하는데 이 부분을 내가 어떻게 적용해야할까?"

### 1. 아키텍처 (Architecture) — "전체 그림"

**의미**: 어떤 조각들이 있고, 그 조각들이 서로 어떻게 소통하는지에 대한 큰 그림. 코드 한 줄 짜기 전에 결정해야 함.

**네 프로젝트에 적용**:
```
[홈페이지]
    └── [연구 시각화 페이지]
            ├── 공통 레이아웃 (탭 전환, 헤더)
            ├── 탭1: 양자구속 계산기
            │     └── 입력(슬라이더) → 계산(JS함수) → 출력(그래프)
            ├── 탭2: 표면/부피 계산기
            │     └── 입력(형태선택+파라미터) → 계산(JS함수) → 출력(숫자+도형)
            └── 탭3: Electron Cloud
                  └── 입력(SMILES) → 파싱(RDKit.js) → 계산 → 출력(색칠된 구조)
```

**효과**:
- 세 계산기가 공통으로 쓸 수 있는 부분(레이아웃, 스타일)과 각자 독립적인 부분(계산 로직)이 명확해짐
- 미리 안 정하면 나중에 하나 고칠 때 다른 게 깨지는 일이 생김

### 2. 폴더 트리 (Folder Tree) — "파일 정리 구조"

아키텍처를 실제 파일/폴더로 옮긴 것.

**예시**:
```
research-visualizations/
├── index.html
├── src/
│   ├── components/
│   │   ├── TabLayout.jsx        (공통 레이아웃)
│   │   ├── QuantumDotCalc.jsx   (탭1)
│   │   ├── SurfaceVolumeCalc.jsx (탭2)
│   │   └── ElectronCloud.jsx    (탭3)
│   ├── physics/
│   │   ├── brusEquation.js      (양자구속 계산 함수)
│   │   └── geometryFormulas.js  (형태별 표면/부피 공식)
│   └── utils/
│       └── colorMapping.js      (파장→색, 전하→색)
└── data/
    └── materialConstants.json   (물질별 유효질량 등 문헌값)
```

> **[실제 채택 구조]** 위 예시는 초기 브레인스토밍 당시 구상이며, 실제 구현은 `js/{pages,features,utils,data}/` 컨벤션으로 진행됨 (계산기 로직은 `js/utils/`, 페이지 진입점은 `js/pages/`, 화면 렌더링/오케스트레이션은 `js/features/`). 이후 계산기 페이지 개발도 이 구조를 따름.

**핵심 이유**:
- "계산 로직(physics/)"과 "화면 표시(components/)"를 분리해두면
- 나중에 물리 공식만 고치고 싶을 때 UI 코드를 안 건드려도 됨
- 유지보수를 Sonnet 같은 저비용 모델에게 맡길 때 특히 중요
- "brusEquation.js 파일의 유전율 값만 수정해줘"처럼 정확히 지시 가능

### 3. 플로우 차트 (Flow Chart) — "동작 순서"

각 기능이 실행될 때 데이터가 어떻게 흐르는지 그림으로 그리는 것.

**양자구속 계산기 예시**:
```
사용자가 슬라이더로 반지름 R 입력
        ↓
selectedMaterial(InP 등)의 상수값 불러오기
        ↓
brusEquation(R, 상수들) 함수 실행
        ↓
결과값(밴드갭 E) → 파장(λ) 변환
        ↓
그래프 업데이트 + 색상 스와치 업데이트
```

**특징**:
- 복잡한 기능일수록 (특히 Electron Cloud처럼 여러 단계를 거치는 경우) 이걸 미리 그려두면
- AI에게 지시할 때 "이 단계에서 이게 안 되면 여기가 문제"라고 디버깅하기 쉬워짐

### 4. 루프 엔지니어링 — 네 프로젝트 규모에는 과할 수 있음

**원래 의미**: 장기간 자율적으로 돌아가는 에이전트 시스템(예: 24시간 코드 자동 수정, 고객 응대 봇)에 필요한 개념

**네 프로젝트의 성격**:
- 정적 웹사이트 하나
- 4일 안에 완성
- 완성 후엔 거의 안 건드림

→ "자가 수정 루프"나 "메모리 루프" 같은 걸 만들 필요가 없음

**대신 실질적으로 적용할 만한 것**: 단순한 버전의 점검 루프

```
Fable5/Sonnet이 코드 작성
        ↓
브라우저에서 직접 실행해보기
        ↓
물리적으로 맞는지 네가 확인 (예: InP 크기 줄이면 청색편이 되는가?)
        ↓
틀리면 → 뭐가 틀렸는지 구체적으로 지적 → 수정 요청
        ↓
맞으면 → 다음 기능으로
```

**정확한 명칭**: 이건 "루프 엔지니어링"이라기보다 그냥 정상적인 개발 사이클(빌드→테스트→수정)

> **[배포 결정]** 배포는 GitHub Pages 사용. 정적 사이트라 별도 빌드 없이 바로 서빙 가능하며, 기존 `.github/workflows/update-citations.yml`과 동일 저장소에서 운영 가능.

### 네 프로젝트에 맞는 활용 순서

   - 구현 직전에 하나씩

4. **루프**
   - 그냥 "만들고 → 검증하고 → 고치고"의 반복이면 충분

## 최종 정리

### 확정된 프로젝트 구조

**홈페이지 내 연구 시각화 페이지 (3가지 기능)**

1. **양자구속 계산기 (EMA/Brus equation)**
   - 역할 분담: Sonnet(문헌값 조사+검증, 코드 작성) → 너(최종 검증)
   - 특징: 해석적 공식, 만들 때만 비용, 이후 무료

2. **표면/부위 비율 계산기 (spherical/tetrahedral)**
   - 역할 분담: Sonnet(기하 공식 유도 + UI/계산 함수)
   - 특징: 동적 파라미터 입력, 기하학 계산, 가벼움

3. **Electron Cloud (Gasteiger charge)**
   - 역할 분담: Sonnet(RDKit.js 리서치 + 파이프라인 구현) → Haiku(텍스트 작성)
   - 특징: SMILES 입력, 부분전하 기반 색상 시각화, 명확한 한계 표시

### 모델별 역할 분담 최종 요약

- **Fable5**: 전체 아키텍처 설계 + 태스크 분배 + 최종 통합 점검
- **Sonnet**: 물리/화학 공식 검증 및 문헌값 조사, 낯선 라이브러리 리서치, 근사 방식 설계, 실제 코드 작성 (함수, UI, 프론트엔드)
- **Haiku**: 텍스트 작성, 단순 색상 함수 등
- **너**: 물리/화학적 타당성 최종 검수, 문헌값 확인
